[[tools-test-distribution]]
= Test Distribution

Citrus Test Distribution partitions and executes JUnit Platform and Citrus integration tests in parallel across remote worker processes, containers, or Kubernetes pods while preserving standard Maven Surefire/Failsafe reports, real-time Web UI observability, and local developer workflows.

[[tools-test-distribution-modules]]
== Modules

* `org.citrusframework:citrus-test-distribution-protocol` — Shared WebSocket/REST protocol DTOs, SHA-256 content-addressed blob cache, Citrus endpoint telemetry collector, capability matcher, and `@LocalOnly` / `@RemoteOnly` / `@AgentRequirement` annotations.
* `org.citrusframework:citrus-test-distribution-ui` — Zero-Node monitoring Web UI served at `/ui/` (overview KPIs, live SVG Gantt partition waterfall, workspace/resource inspector, worker pool health, test history/flakiness, and failing test / partition crash diagnostics).
* `org.citrusframework:citrus-test-distribution-coordinator` — Vert.x HTTP/WebSocket coordinator, Longest-Processing-Time (LPT) scheduler, SSE event hub, and JDBC persistence (file-backed `HSQLDB` or `PostgreSQL`).
* `org.citrusframework:citrus-test-distribution-worker` — Standalone Java worker runtime with child-first `ClassLoader` or forked-JVM workspace isolation and graceful `SIGTERM` draining (`citrus-agent --mode worker` or `citrus dist worker start`).
* `org.citrusframework:citrus-test-distribution` — JUnit Platform launcher interceptor, `@LocalOnly` / lost-partition local fallback executor, Surefire XML writer, and `@CitrusTestFactory` declarative source splitter.
* `org.citrusframework.mvn:citrus-test-distribution-maven-extension` — Opt-in Maven Core Extension (`-Dcitrus.test.distribution.enabled=true`) coordinating reactor-wide build sessions.

[[tools-test-distribution-architecture]]
== Architecture and Execution Flow

A distributed test run involves three components:

. *Build Host (Maven Extension + JUnit `LauncherInterceptor`):* Opens a single build session on the coordinator (recording project name, Git branch, commit SHA, and changed workspace files), discovers JUnit Platform test descriptors per module, executes `@LocalOnly` tests locally, packages the test classpath and any declared external input paths into SHA-256 content-addressed blobs, uploads only missing digests, submits remote work units, streams live test and partition events over Server-Sent Events (SSE), writes standard `TEST-*.xml` Surefire/Failsafe reports, and atomically commits any declared output files back into the module.
. *Coordinator (`DistributionCoordinatorServer`):* Persists sessions, partitions, worker leases, and historical test durations in JDBC (`HSQLDB` or `PostgreSQL`), schedules work units onto capability-matching workers using Longest-Processing-Time (LPT) bin packing seeded from historical execution times (choosing an eligible idle worker by pool priority and then favoring workers least recently assigned), deduplicates classpath/workspace blobs on disk, monitors worker heartbeats, automatically requeues evicted or stalled partitions up to `maxRetries`, and serves the real-time Web UI and REST/SSE APIs.
. *Workers (`DistributionWorkerClient`):* Maintain outbound WebSocket connections (`/ws/v1/worker`) to the coordinator, advertise auto-detected host capabilities (`os`, `arch`, `jdk`, `cpuCores`, `memoryMb`, `citrus.workspace.v1`) plus user tags, pull missing blobs into a local content-addressed cache, execute assigned partitions in a forked JVM (default) or, with `forkMode=AUTO`, an isolated child-first `ClassLoader` inside the worker JVM, stream per-test outcomes and captured Citrus endpoint names, and drain cleanly on `SIGTERM`.

[[tools-test-distribution-maven]]
== Maven Quickstart and Build Host Settings

Register the extension in `.mvn/extensions.xml`:

[source,xml]
----
<extensions xmlns="http://maven.apache.org/EXTENSIONS/1.0.0">
  <extension>
    <groupId>org.citrusframework.mvn</groupId>
    <artifactId>citrus-test-distribution-maven-extension</artifactId>
    <version>${citrus.version}</version>
  </extension>
</extensions>
----

Start a coordinator and worker pool via `citrus-jbang`, then run Maven with distribution enabled:

[source,bash]
----
citrus dist coordinator start --port=18080
citrus dist worker start --coordinator-url=http://127.0.0.1:18080 --capabilities=docker=true

./mvnw verify \
  -Dcitrus.test.distribution.enabled=true \
  -Dcitrus.test.distribution.coordinatorUrl=http://127.0.0.1:18080
----

Normal Maven builds without `-Dcitrus.test.distribution.enabled=true` execute locally with zero coordinator traffic. In multi-module Maven reactors, the extension automatically shares one coordinator `sessionId` across all modules, reports both remote partitions and `@LocalOnly` module executions into that session, and aborts the session on the coordinator if the Maven build is interrupted (`Ctrl+C`).

TestNG modules can use distribution with the `surefire-junit-platform` provider and
`org.junit.support:testng-engine` as a test-scoped project dependency. The engine maps TestNG groups to
JUnit Platform tags, so Surefire and Failsafe group filters apply before work is sent to workers.

TIP: Projects that do not use the Maven extension can add `org.citrusframework:citrus-test-distribution` to the test runtime classpath and enable JUnit Platform interceptor discovery (`-Djunit.platform.launcher.interceptors.enabled=true -Dcitrus.test.distribution.enabled=true`).

To start a PostgreSQL-backed coordinator and a local worker pool in containers, see <<tools-test-distribution-docker>>.

Local bypass applies when the selection has no `@RemoteOnly` tests, remote capability requirements, declared workspace inputs or outputs, or explicit workspace fork. The launcher runs the discovered tests directly and reports the results to an existing Maven reactor session, when present. Scheduling and warm bypass use timing history scoped to the Maven root group ID and artifact ID. Set `citrus.test.distribution.projectKey` to distinguish builds that share coordinates. Older sessions without a project key retain their recorded timing history under their project name.

For module-level workspace and isolation settings (`inputs`, `outputs`, `fork`, `partitionPolicy`, `skip`), see <<tools-test-distribution-external-resources>>.

[[tools-test-distribution-docker]]
== Docker Compose

With Docker and Docker Compose installed, run the start script from the Citrus checkout. It builds separate,
non-root coordinator and worker images from the same source tree, starts PostgreSQL 16, and runs eight Java 21
workers. PostgreSQL must be ready before the coordinator starts, and the coordinator must be healthy before the
workers start. Only the coordinator publishes a host port, bound to loopback.

[source,bash]
----
./tools/citrus-test-distribution/docker/start.sh
----

The script prints the dashboard URL and opens it on a supported desktop after startup. The default is
http://127.0.0.1:8765/ui/. On a headless machine, use the URL printed in the terminal. Check the Workers view for
eight connected workers.

=== Run modules from the Citrus checkout

With the stack running, run the tests for one module by its Maven artifact ID or reactor path.

[source,bash]
----
./tools/citrus-test-distribution/docker/run-tests.sh -module citrus-api
----

Use `-all` in place of `-module citrus-api` to run `verify` across the whole reactor. The runner builds
the distribution extension and any prerequisites in a checkout-local Maven repository with tests skipped.
It loads the extension from a temporary Maven configuration for the test run.

The runner uses the published coordinator port for the selected Compose project. You can export
`CITRUS_DIST_COORDINATOR_URL` to set the address explicitly. Export the same `CITRUS_DIST_AUTH_TOKEN` as
the stack if you enabled authentication. The runner disables local fallback with
`-Dcitrus.test.distribution.fallbackLocal=false` and sets both
`-Dcitrus.test.distribution.minRemoteDurationMs=0` and `-Dcitrus.test.distribution.minRemoteColdUnits=0`
so duration and cold-start thresholds allow eligible tests to run on the workers. The normal test placement
rules still apply. Tests that use external services or tools require those dependencies in their execution environment.

Register the Maven extension as shown in <<tools-test-distribution-maven>>, then run your tests on the host.

=== Stop or remove the stack

Use the stop script to pause services and preserve their containers, images, and data.

[source,bash]
----
./tools/citrus-test-distribution/docker/stop.sh
----

The worker gives an active partition up to 30 seconds to finish. Compose gives the container a shutdown
grace period of 65 seconds, which also covers closing connections and releasing resources.
Starting again with the same source and settings reuses worker identities and caches. PostgreSQL and the
coordinator artifact cache use named volumes, so their data also survives container recreation. Replacing a
worker starts it with a fresh cache.

For a fresh stack, run the cleanup script. It deletes the selected Compose project's containers and networks,
both source-built Citrus images, and the named volumes holding test history and artifacts.

[source,bash]
----
./tools/citrus-test-distribution/docker/clean.sh --yes
----

=== Run a worker against an existing coordinator

Build the `worker` image target and pass the reachable coordinator URL via the environment. The dedicated worker
opens an outbound connection and needs zero published ports.

[source,bash]
----
docker build -f tools/citrus-test-distribution/docker/Dockerfile --target worker -t citrus-dist-worker .
docker run -d --init --stop-timeout 65 \
  -e CITRUS_DIST_COORDINATOR_URL=https://coordinator.example.org \
  -e CITRUS_DIST_AUTH_TOKEN \
  citrus-dist-worker
----

For a pooled worker, also pass `-e CITRUS_DIST_WORKER_POOL -e CITRUS_DIST_WORKER_REGISTRATION_KEY` after exporting
the corresponding values. Use the same settings and CLI options as <<tools-test-distribution-workers>>.
For workloads that require another JDK or tools, extend the worker image with the required software.

[[tools-test-distribution-coordinator]]
== Coordinator, CLI, and REST API

The coordinator (`citrus-test-distribution-coordinator`) runs an embedded Vert.x HTTP/WebSocket server backed by a content-addressed filesystem blob cache and a JDBC telemetry store (`HSQLDB` by default, or `PostgreSQL` for shared CI deployments).

[cols="3,5,1",options="header"]
|===
|Property / environment variable |Description |Default

|`citrus.test.distribution.coordinator.minPartitionDurationMs` / `CITRUS_DIST_COORDINATOR_MIN_PARTITION_DURATION_MS`
|Target minimum estimated duration of an adaptive LPT partition in milliseconds. Set to `0` to disable the duration target.
|`5000`

|`citrus.test.distribution.coordinator.maxWavesPerWorker` / `CITRUS_DIST_COORDINATOR_MAX_WAVES_PER_WORKER`
|Target maximum number of adaptive LPT partitions per eligible worker. Set to `0` to disable the wave target.
|`2`

|`citrus.test.distribution.coordinator.requireAgentPool` / `CITRUS_DIST_COORDINATOR_REQUIRE_AGENT_POOL`
|Require every new worker registration to include a pool ID and valid key. Enable this after migrating unpooled workers.
|`false`
|===

Adaptive sizing applies to LPT submissions that do not declare workspace outputs and leave `maxPartitionSize` unset.

=== Recovering a distributed run after a process crash

Use file-backed HSQLDB or PostgreSQL for the coordinator and keep its artifact cache on persistent storage.
Queued work, dispatch instructions, partition attempts, retry limits, results, and the event stream are stored in JDBC.
After a coordinator restart, pending work becomes available to reconnecting workers. Interrupted attempts are retried
under the original policy, and the previous attempts remain visible in the session history.

Use a persistent cache directory for each worker and keep the same worker identity when restarting it. The worker writes
test events and partition completions to its on-disk journal and removes them after the coordinator acknowledges them.
The coordinator keeps a record of accepted delivery IDs, so repeating a delivery does not create another test result.

If Maven or its test JVM exits abruptly, use the same checkout, Maven goals, selectors, and options, and add the existing
running session ID from the log or dashboard:

[source,shell]
----
./mvnw verify -Dcitrus.test.distribution.enabled=true \
  -Dcitrus.test.distribution.resumeSessionId=sess-your-session-id
----

Keep the same coordinator URL and local user account. Maven reuses the existing remote submissions for each test plugin
execution and reads their stored events to recreate test reports. Launcher-managed local test results are journaled under
`${user.home}/.citrus/distribution-local-results` until accepted. A deliberate session abort remains terminal.

Event replay is available for events written after the upgrade. Existing session, partition, and test result records stay
available in the dashboard. Saved dispatch instructions include the system properties forwarded to the test JVM.

=== JBang CLI Commands

`citrus-jbang` ships built-in subcommands under `citrus dist` for starting and inspecting a distribution cluster:

[source,bash]
----
# Start coordinator and Web UI on port 8765
citrus dist coordinator start --port=8765

# Start coordinator backed by PostgreSQL and Bearer token auth
citrus dist coordinator start \
  --host=0.0.0.0 \
  --port=8765 \
  --jdbc-url=jdbc:postgresql://db.internal:5432/citrus_dist \
  --cache-dir=/var/lib/citrus/blobs \
  --auth-token=secret-ci-token

# Check coordinator health and connected worker pool
citrus dist status --coordinator-url=http://localhost:8765 --auth-token=secret-ci-token

# List recent build sessions (table or --json)
citrus dist sessions --coordinator-url=http://localhost:8765 --limit=20

[[tools-test-distribution-ui]]
== Distribution Web UI

Whenever `citrus-test-distribution-ui` is on the coordinator classpath (included automatically by `citrus-test-distribution-coordinator` and `citrus-jbang`), the coordinator serves the Distribution Web UI at `http://<host>:<port>/ui/`.

The UI is a zero-Node ES module single-page application built with lightweight `htm` virtual DOM templates and SVG charts, requiring no external build toolchain or CDN access.

=== Real-Time Transport, Deep Links, and Authentication

* *Live SSE with Automatic Polling Fallback:* On load, the UI opens an `EventSource` stream against `/api/v1/events/stream` (`Live SSE` badge in the top bar) and coalesces burst events so rapid `test.event` updates refresh views smoothly without flooding the browser. If SSE disconnects or is blocked by a reverse proxy, the UI switches to a 4-second background HTTP polling loop (`Polling` badge), ticks elapsed clocks for `RUNNING` sessions locally, and automatically reconnects `EventSource` once the coordinator becomes reachable again.
* *URL Hash Routing:* Views and session sub-tabs synchronize with the URL hash (`#overview`, `#sessions`, `#session/<sessionId>/<tab>`, `#workers`, `#pools`, `#usage`, `#history`), preserving navigation state across browser reloads and shareable links.
* *Authenticated Dashboard Access:* To serve the dashboard on a coordinator with bearer authentication enabled, use a trusted reverse proxy that supplies the bearer header for the dashboard’s API and SSE requests.
* *Theme Toggle:* The sun/moon toggle switches between dark and light themes.

=== UI Views and Telemetry Binding

==== Overview Dashboard (`#overview`)

Provides fleet-wide KPIs across recent sessions and workers:

* *Build Sessions* and *Session Pass Rate* (`PASSED` out of completed sessions).
* *Online Workers* (non-`OFFLINE` workers — `IDLE`, `BUSY`, and `DRAINING` — vs total registered fleet).
* *Distribution Speedup* (aggregate serial test time divided by distributed wall-clock duration) and *Blob Cache Efficiency* (`cachedBlobs / totalBlobs`).
* *Flaky Tests Detected* (tests that failed or were interrupted on an initial attempt and passed on automatic partition retry), plus quick-jump tables for *Recent Build Sessions* and *Worker Pool Health*.

==== Build Sessions Explorer (`#sessions`)

Lists build sessions, named after the root Maven project (hover the name for the modules the session ran), with instant text filtering by session ID, Git branch, commit SHA, or project name, and status filter pills (`ALL`, `RUNNING`, `PASSED`, `FAILED`, `ABORTED`). `RUNNING` sessions display live-updated test progress bars, blob cache hit percentages, and elapsed wall time as partitions and `@LocalOnly` tests report in.

==== Session Waterfall and Inspector (`#session/<sessionId>/<tab>`)

Inspects a single build session across five session KPIs (`Passed Tests`, `Failed Tests`, `Flaky Recovered`, `Wall vs Serial Time`, `Blob Cache Hit`), an `✕ Abort Session` control while `RUNNING`, a banner with the failure reason of a `FAILED` session (for example the failing module and its failed test count), and four sub-tabs:

* *Execution Waterfall (`waterfall`):* Renders an interactive worker-swimlane SVG Gantt chart of all partition attempts, colored by Maven module with a legend, alongside the *Partition Breakdown* table. When a worker disconnects or stalls mid-partition, attempt `#1` remains visible as `LOST` on the original worker swimlane while attempt `#2` renders on the recovery worker swimlane. Clicking any waterfall bar or partition row opens the *Partition Detail Modal* showing state, attempt number, worker assignment, required capabilities, Failure / Eviction Reason (`errorMessage`), *Workspace & External Test Resources* (`moduleName`, `forkWorkspace` isolation mode, `workingDirectory`, materialized `inputPaths`, declared `outputPaths`, and collected `producedOutputs`), work units, and executed tests.
* *Test Executions (`tests`):* Lists every remote and `@LocalOnly` test execution with status pills (`ALL`, `FAILED`, `FLAKY`, `PASSED`, `SKIPPED`) and search across test class, method, worker ID, or *Citrus Endpoints*. During execution on both remote workers and local fallback runs, Citrus automatically hooks `CitrusInstanceManager` / `TestActionListener` to record the deduplicated Citrus endpoint names (or endpoint URIs) exercised by each test, displaying them as inline badges and in the *Test Execution Detail Modal*.
* *Failing Tests (`failures`):* Surfaces full stack traces with one-click `Copy Trace` buttons for every `FAILED` test execution, *and* renders partition-level crash or eviction diagnostic cards whenever a partition fails or is lost (`FAILED` or `LOST` with `errorMessage`) — ensuring forked JVM crashes, `ClassNotFoundException`, undeclared working-directory writes (`cwdCheck=FAIL`), or aborted partitions are immediately visible even when zero individual JUnit tests completed.
* *Changed Files (`files`):* Shows the status of each tracked workspace file captured when the Maven session started. Expand a file to see its captured Git diff preview and line counts where available. The coordinator stores at most 8 KiB of preview output per file and 32 KiB per session. Older sessions display the recorded file paths.

Long lists (build sessions, partitions, test executions and test history) are paginated; a table returns to its first page when the selected session or one of its filters changes.

==== Workers Pool (`#workers`)

Workers appear in tables grouped by pool, with a separate group for unpooled workers. Each row shows the worker ID,
host, version, capabilities, state, last heartbeat, and current test or partition. Search by ID, host, or capability
and select *Warning* to see workers with a pool or key warning and the time until their disconnect deadline.
Workers that report local file cache statistics show the cleanup policy, cached blob count and size, usable disk space,
and eviction count. The *Low Disk* filter selects workers whose usable disk space is below their configured buffer.

[[tools-test-distribution-agent-pools]]
==== Agent Pools (`#pools`)

Create a pool with a display name and the capabilities every member must advertise. The coordinator assigns a unique,
stable pool ID. Copy that ID into the worker configuration. For example, a pool with `docker` and `jdk=21` admits
Java 21 workers advertising `docker=true`. A bare capability means `true`. In a REST request, supply string values,
for example `{"displayName":"Container workers","capabilities":{"docker":"true","jdk":"21"},"generateRegistrationKey":true}`.

For a partition to run on a pooled worker, both the pool's declared capabilities and the worker's advertised capabilities
must satisfy every partition requirement. Declare built-in capabilities on the pool when jobs require them. For example,
include `citrus.workspace.v1=true` for jobs that declare workspace inputs or outputs. Workers may advertise extra
capabilities. Capability values match without regard to case. Numeric `cpuCores` and `memoryMb` requirements are minimums.

Drag a pool or use *Up* and *Down* to change the order. The coordinator checks the highest-priority pool first
(`priorityOrder=0`). If its matching workers are busy or unavailable, an idle matching worker from the next pool can take
the partition immediately. Configured pools take priority over eligible unpooled workers.

===== Registration keys and grace windows

Generate a registration key on creation or under *Manage* → *Registration Keys*. Copy the full `ctrk_...` value into
the worker's secret configuration while it is displayed. The coordinator stores its hash. Subsequent reads and dashboard
visits show the key prefix, description, last use, and revocation status. Citrus Agent omits the secret from its
configuration responses and masks the registration-key property in configuration logs. The pool key authenticates
registration and renewal. A coordinator configured with bearer authentication also requires its auth token.

A pool can have multiple active keys. To rotate, generate a replacement, update the affected workers' configuration,
and restart them with the new key. Confirm successful registration and the new key's *Last used* details before
revoking the old key. Workers use their startup credential for every renewal.

[cols="2,4",options="header"]
|===
|Workers Pool warning |What happens
|`KEY_REVOKED`
|New registrations with that key fail immediately. Connected workers using it disconnect on their next renewal
(normally hourly) or at the one-hour deadline, whichever comes first.
|`POOL_CAPABILITY_MISMATCH`
|After a pool edit, connected workers that no longer satisfy all mandatory capabilities have four hours to comply.
They can still receive work matching both sets of capabilities during the grace window. Restart with the required
capabilities or correct the pool definition before the deadline.
|`POOL_DELETED`
|The coordinator immediately stops assigning new partitions from the deleted pool. Connected workers have a four-hour
grace window for existing work. Reconfigure and restart them with another pool and its key.
|===

==== Historical Usage (`#usage`)

Choose *1 hour*, *24 hours*, or *7 days* to see active jobs, fleet utilization, and utilization for each pool.
The REST response also reports active partitions in the fleet series. *Connected* counts online workers, *Utilized* counts workers handling work, and *Desired* counts active and
pending partitions. Per-pool desired demand fills compatible pools by priority up to their connected capacity.
Excess demand goes to the highest-priority compatible pool. Deleted pools retain connected and utilized counts while
their workers remain connected during grace and receive no new desired demand.

Filter by capability or requirement, for example `docker,jdk=21`. The filter applies to job requirements, pool
capabilities, and capabilities advertised by unpooled workers. All filter terms must match. Each chart bucket shows
the peak of each metric in that interval. Use the pointer or arrow keys to inspect it.

The coordinator samples every 15 seconds and retains seven days by default. Embedded coordinators can change these
defaults with `DistributionCoordinatorConfig.Builder.usageSampleIntervalMs` and `usageRetentionMs`.
The dashboard uses the interval from the usage response header `X-Citrus-Usage-Sample-Interval-Ms` to refresh the charts.

==== Test History and Flakiness (`#history`)

Search cross-session test history by project, class, or method. The sidebar's flaky count opens the *Flaky* filter
(`#history?outcome=flaky`), which shows tests that passed on a worker retry. Choose *View runs* to see attempts
grouped by build session and open the session that recorded a recovery.

[[tools-test-distribution-workers]]
== Test Distribution Workers

A worker connects to a coordinator over an outbound WebSocket, downloads the files it needs, executes one test
partition at a time and streams results back. Both runtimes use the same worker client. Choose
`citrus dist worker start` for a dedicated worker in a CI job or container. Choose Citrus Agent in worker mode
when you also need its HTTP service, Web UI or on-demand test runs.

=== Start a worker

Start the coordinator separately with `citrus dist coordinator start`. It listens on port `8765` by default.
For a pooled worker, create an <<tools-test-distribution-agent-pools,agent pool>> and supply its ID and registration
key. The examples read those values from the environment. If your coordinator accepts unpooled workers, you can
omit both settings. A coordinator with bearer authentication also requires `CITRUS_DIST_AUTH_TOKEN` or `--auth-token`.

.Dedicated JBang worker
[source,bash]
----
citrus dist worker start \
  --coordinator-url=http://localhost:8765 \
  --pool="$CITRUS_DIST_WORKER_POOL" \
  --registration-key="$CITRUS_DIST_WORKER_REGISTRATION_KEY"
----

.Citrus Agent with its packaged JAR and adjacent lib/ directory
[source,bash]
----
java -jar citrus-agent.jar --mode worker \
  -u http://localhost:8765 \
  --pool "$CITRUS_DIST_WORKER_POOL" \
  --registration-key "$CITRUS_DIST_WORKER_REGISTRATION_KEY"
----

The JBang worker defaults to `http://localhost:8765`. Citrus Agent defaults to `http://localhost:8084`.
To point the agent at a coordinator on port `8765`, set `-u` / `--coordinator-url`,
`citrus.test.distribution.coordinatorUrl` or `CITRUS_DIST_COORDINATOR_URL`. In a container, use the coordinator's
reachable hostname. See <<agent-worker-mode>> for environment-only startup.

=== Environment variables and JVM system properties

Explicit worker options override inherited settings. Both runtimes use the following lookup order.

* For coordinator URL, bearer token and cache settings, the worker checks the JVM system property, then the
  `CITRUS_DIST_*` environment variable, then uses the runtime default. Cache settings also accept the existing
  `TEST_DISTRIBUTION_AGENT_*` aliases listed under <<tools-test-distribution-external-resources-worker>>
  after the Citrus environment variable.
* For pool ID, registration key, worker ID and capabilities, the worker checks the `CITRUS_DIST_WORKER_*`
  environment variable before the `citrus.test.distribution.worker.*` JVM system property, then uses the runtime
  default. Existing environment aliases are checked after the Citrus variable and before the system property.
  The pool and registration key aliases are `TEST_DISTRIBUTION_AGENT_POOL` and `TEST_DISTRIBUTION_AGENT_REGISTRATION_KEY`.
* Citrus Agent reads `citrus.agent.mode`, or `CITRUS_AGENT_MODE` if the JVM property is unset. A blank or unset
  inherited mode selects `standalone`. The agent validates this setting before reading CLI options, so an unsupported
  value stops startup. Use `--mode` to override a valid inherited mode.

=== Worker capabilities

The worker detects `os`, `arch`, `jdk` (Java feature version), `cpuCores` (available processors) and `memoryMb`
(maximum JVM heap in MiB). It advertises workspace support by default with `citrus.workspace.v1`,
`citrus.workspace.quarkus.v1`, `citrus.workspace.jvm-options.v1` and `citrus.workspace.jvm-layout.v1`, each set to `true`.

Use `CITRUS_DIST_WORKER_CAPABILITIES` or its system property to add or override tags. A bare tag means `true`.
The worker merges `-C` / `--capabilities` entries over the inherited tags. For example, with
`CITRUS_DIST_WORKER_CAPABILITIES=zone=east,large-fixtures`, passing `-C zone=west` advertises `zone=west`
and `large-fixtures=true`. The runtime always reports its actual `jdk` and sets the protocol marker `citrus-worker=true`.

=== Local file cache

The worker keeps downloaded classpath JARs and declared inputs across partitions, sessions and restarts. Set
`--cache-dir` to choose a directory. The default is `${user.home}/.citrus-test-distribution-agent/file-cache`.
The worker verifies files before reuse, removes corrupt files and downloads them again. A download that receives
no data for 60 seconds fails the partition and removes the partial file.

With cleanup enabled, the worker checks free space at startup, before each download and after each partition.
When space falls below `--cache-free-space-buffer-size`, it evicts the least recently used files first and preserves
files in use by the running partition. Specify the buffer in bytes or whole `KiB`, `MiB` or `GiB` (case-insensitive).
If eviction cannot restore the buffer, the worker warns and continues. A full disk can fail the partition.
On small disks, lower the buffer to avoid repeatedly emptying the cache.

Use `--no-cache-cleanup` or `--cache-cleanup false` to let the cache grow without automatic eviction. Both runtimes
accept a space-separated boolean or an equals sign. If a cleanup flag is repeated, the last value wins.
Both runtimes validate cache flags even with `--help` or `-h`.

Each worker holds an exclusive `<cacheDir>/.lock` on a local filesystem that supports file locking. Give every worker
on a host its own cache directory. A worker refuses a directory locked by another worker or marked for use by a
coordinator or build host.

NOTE: Older versions used `.citrus-dist/cache/worker` under the working directory. After upgrading, you can delete
the unused old directory. Workers running under the same account now share the default path, so set a distinct
`--cache-dir` for each.

=== Registration and shutdown

Upgrade the coordinator before enabling pooled workers. A pooled worker requires the coordinator to confirm its
pool ID before it accepts work. Once confirmed, it renews its registration hourly using its startup key.
See <<tools-test-distribution-agent-pools>> for key rotation and grace periods.

[cols="2,3",options="header"]
|===
|Registration rejection |What to check

|`POOL_REQUIRED`, `POOL_NOT_FOUND` |Supply the ID of an existing pool.
|`INVALID_REGISTRATION_KEY`, `REVOKED_REGISTRATION_KEY` |Use an active key issued for that pool.
|`MISSING_POOL_CAPABILITIES` |Compare the worker's advertised tags with the pool's mandatory capabilities.
|`INVALID_WORKER_METADATA` |Use at most 128 characters for the worker ID and 255 for the hostname.
|`ALREADY_REGISTERED` |The same connection attempted to register twice.
|`POOL_NOT_CONFIRMED` |The worker could not confirm its configured pool. Check the coordinator version and pool ID.
|`WORKER_REJECTED` |The worker received a rejection without a specific reason. Check the coordinator logs.
|===

On registration rejection, the JBang worker reports the reason and exits with a nonzero status. Citrus Agent
logs one warning and keeps its HTTP service running. Check the coordinator's worker list to verify registration.
On `SIGTERM`, the worker signals `worker.draining` so the coordinator stops assigning it new partitions.
The JBang worker gives an active partition up to 30 seconds to finish. Citrus Agent allows up to 15 seconds.
The worker then closes the connection and releases the cache lock.

[[tools-test-distribution-annotations]]
== Placement Annotations

* `@LocalOnly` — Pins a test class or method to the build host JVM by default. Local executions are reported under `partitionId="local"`.
* `@RemoteOnly` — Requires execution on a remote worker and fails fast when the coordinator is unreachable regardless of `fallbackLocal`.
* `@AgentRequirement(key = "docker", value = "true")` — Repeatable capability filter matched against registered worker capabilities. Supports exact string matching (`os=linux`, `docker=true`) and numeric threshold expressions (`memoryMb>=4096`, `cpuCores>=4`, `jdk>=21`).

`@Nested` test classes are distributed as work units of their own and inherit these annotations from the classes enclosing them.

[source,java]
----
@CitrusSupport
@AgentRequirement(key = "docker", value = "true")
@AgentRequirement(key = "memoryMb", value = ">=4096")
class KafkaTestcontainersIT implements TestActionSupport {

    @Test
    @CitrusTest
    void shouldConsumeOrderEvents() {
        // Scheduled only on workers advertising docker=true and memoryMb >= 4096
    }

    @Test
    @LocalOnly
    void shouldInspectDeveloperLocalKeystore() {
        // Runs on the local build machine by default
    }
}
----

Declarative XML and YAML tests produced via `@CitrusTestFactory` are also split into individual distributable work units so large declarative test suites scale across workers automatically.

=== Opting local tests into worker execution

Use these JVM properties on a distribution-enabled Maven invocation. Scope each invocation to the intended module
with `-pl` so supplemental classpath entries apply only where needed.

* `citrus.test.distribution.remoteLocalOnlyClasses` takes comma-separated fully qualified class names.
  It clears the class-level pin for each selected class.
* `citrus.test.distribution.remoteLocalOnlyMethods` takes comma-separated selectors such as
  `com.example.ExampleTest#shouldRun`. For methods with parameters, use the signature, for example
  `com.example.ExampleTest#run(java.lang.String,int)`. A class or enclosing class can still pin the method locally.
* `citrus.test.distribution.additionalWorkerClasspath` takes existing host directories and JARs separated by the
  host's Java classpath separator (`:` on Unix and `;` on Windows). Distribution transfers the entries, appends them
  to the worker classpath and forks the partition JVM. It does not change the Maven host classpath.

An opt-in makes a test eligible for distribution. Normal placement rules, including warm local bypass and local
fallback, still apply. For a worker-only verification, disable local fallback and set both local bypass thresholds
(`minRemoteDurationMs` and `minRemoteColdUnits`) to zero. A test with an effective `@RemoteOnly` requirement is
ineligible for local execution.

A nested launcher stays on the host when it runs on a thread executing the local test plan. When a test submits its
embedded JUnit launch to a separate executor, set the per-request configuration parameter
`citrus.junit.jupiter.embeddedLauncher=true` on its discovery request. Independent launches, including direct calls
to the Citrus Jupiter engine, use normal placement rules.


=== Citrus suites that require workers

With distribution enabled, the Citrus JBang CLI `RunTest`, the four external-process methods in
`JBangTestEngineTest`, and the Quarkus `DemoApplicationTest` require workers through `@RemoteOnly`.
Normal Maven builds with distribution disabled can run these tests locally.

The JBang CLI test classpath includes its Groovy and Cucumber modules. Reactor builds require workers that preserve
module names in classpath directory entries. The connector workers need Java and JBang.
Set `CITRUS_JBANG_EXECUTABLE` on a worker to select a provisioned executable. Workers need access to the JBang app
catalog and its dependencies or an already populated cache. Distribution serializes partitions containing Jupiter
`@Isolated` classes or their nested tests that share the same JVM user home, including local distribution fallback.

Quarkus tests require workers advertising `citrus.workspace.quarkus.v1=true`. The launcher reads the model path
supplied by Quarkus, transfers the generated model and its dependencies, and remaps their paths in the forked
worker workspace. Quarkus versions with JSON model support can use either JSON or Java serialization on the build host.
Custom Quarkus class output directories still need to be supported by the Quarkus test launcher, including
`TEST_TO_MAIN_MAPPINGS` where applicable.

[source,bash]
----
./mvnw test -pl runtime/citrus-quarkus/citrus-quarkus-it -Dtest=DemoApplicationTest \
  -Dcitrus.test.distribution.enabled=true
----

[[tools-test-distribution-external-resources]]
== External Test Resources

Remote workers receive the module's test classpath (compiled classes, copied test resources, and dependency jars).
Tests that read or write files outside the classpath, or that change JVM-wide state, need a few module settings so they
behave on a worker exactly as they do locally.

[[tools-test-distribution-external-resources-settings]]
=== Module settings

All settings are plain Maven properties, so `./mvnw test` behaves the same with and without the distribution extension.

[cols="2,4,1",options="header"]
|===
|Property |Meaning |Default
|`citrus.test.distribution.inputs`
|Comma-separated paths, relative to the module directory, copied into the worker workspace before the tests run.
A `?` before or after a path marks it optional (skipped when absent); a missing required path fails the build before
anything is submitted.
|none
|`citrus.test.distribution.outputs`
|Comma-separated paths, relative to the module directory. Files the tests create or change under them on the worker
are copied back into the module afterwards (see <<tools-test-distribution-external-resources-outputs>>). The optional
marker `?` is not allowed here.
|none
|`citrus.test.distribution.fork`
|`true` runs the module's partitions in a short-lived JVM on the worker instead of the shared worker JVM. Declaring
inputs or outputs implies a forked JVM.
|`false`
|`citrus.test.distribution.partitionPolicy`
|`LPT` splits the module's tests into several partitions by historical duration; `SINGLE` runs all of them in one
partition and workspace (for tests that depend on files written by other test classes). Under `SINGLE`, tests requiring
different values for the same capability are rejected.
|`LPT`
|`citrus.test.distribution.skip`
|`true` keeps the module's tests local, exactly as without Test Distribution. Set it to `false` on the command
line to override a module's skip setting for an opt-in run. The value is taken from the command line, then the
module's `<properties>`, then the environment variable `CITRUS_DIST_SKIP`.
|`false`
|===

[source,xml]
----
<properties>
  <citrus.test.distribution.inputs>target/generated-test-sources,?src/test/data</citrus.test.distribution.inputs>
  <citrus.test.distribution.fork>true</citrus.test.distribution.fork>
</properties>
----

Paths use `/` (a `\` is converted); a leading `./` and a trailing `/` are dropped, and a path below another declared
path is covered by it.

Each setting is taken from the first of these that defines it; lower levels are replaced, never merged (levels 2 and 3
are applied by the Maven extension; without it, the test JVM sees the system property and the environment variable):

. The Maven command line (`-Dcitrus.test.distribution.inputs=...`).
. An explicit `<systemPropertyVariables>` value of the Surefire or Failsafe configuration.
. The module's `<properties>` (inherited from parent POMs as usual).
. The environment variables `CITRUS_DIST_INPUTS`, `CITRUS_DIST_OUTPUTS`, `CITRUS_DIST_FORK`, `CITRUS_DIST_PARTITION_POLICY`.
. The default.

The value `none` clears a path list at any level, for example to drop paths inherited from a parent POM. Empty values
count as unset. With the Maven extension, an empty command-line value (`-Dcitrus.test.distribution.inputs=`) also
clears the setting; without it, use `none`. Invalid `fork` or `partitionPolicy` values fail the build at startup with
the module and the source of the value.

[[tools-test-distribution-external-resources-when]]
=== Choosing settings

* *Files read from disk, not from the classpath:* declare them as `inputs`. Anything under `src/test/resources` is
copied to `target/test-classes`, which is on the classpath, and needs no declaration when read through the classpath.
On a worker, classpath directories are unpacked to a different location than locally: tests must not derive file paths
from a class or resource location (for example `getResource(...).getFile()` followed by string replacements). Use
`System.getProperty("basedir")` to locate module files instead.
* *Files written relative to the working directory, temporary files with fixed names, JVM-wide changes* (Log4j levels,
default locale or time zone, static caches) *or servers on fixed ports:* set `fork=true` so the partition is forked even
on workers running with `forkMode=AUTO`. In the shared worker JVM a
read-only check of the worker's working directory fails the partition when a test wrote there (see `cwdCheck` below);
nothing is ever deleted.
* *Generated files needed on the developer machine after the tests:* declare them as `outputs`.
* *Tests that depend on the developer machine itself* (installed tools, the local Maven repository, an application
started locally): annotate them with `@LocalOnly` (test-scoped dependency
`org.citrusframework:citrus-test-distribution-protocol`).

[[tools-test-distribution-external-resources-workspace]]
=== Working directory, basedir and path rewriting

A forked partition runs in a private workspace that mirrors the module directory: inputs are materialized at their
module-relative paths and `target/` exists from the start. The test JVM starts in the same relative working directory as
the local one — `target/` for Surefire tests in the Citrus build, the module directory for Failsafe tests — and the
`basedir` system property points at the workspace root.

System properties forwarded to workers that contain the module path (for example `project.build.directory` or a
configured file path) are rewritten to the workspace: the module path is replaced by the token `${citrus.dist.workspace}`
on the host and expanded on the worker. Only whole path segments are replaced (a sibling such as `/work/app-other` stays
untouched), including inside `file:` URIs, JDBC URLs, path lists and `@argument` files. Windows path separators inside
matched paths are normalized for transfer. URL-encoded paths and embedded path-list delimiters retain their original
form.

Citrus Test Distribution forwards assertion settings, portable module-access options and `--enable-preview` from
the build test JVM to a compatible forked worker. Module paths and patched modules are rebuilt from transferred
artifacts. Workers must meet the minimum Java release of the transferred bytecode, and tests using preview features
require the same Java release. Configure worker-specific JVM options such as heap limits and agent paths with
`citrus.test.distribution.worker.forkJvmArgs`. Maven reactor directory entries use their effective output directories
and artifact IDs when available.

When the effective Maven build directory is outside the module, its class outputs, forwarded system properties
and the test JVM's working directory are mapped into a private area of the worker workspace.

[[tools-test-distribution-external-resources-outputs]]
=== Outputs

Output files are collected from every partition and written into the module only after all partitions finished:

* Only files new or changed during the run are copied; unchanged inputs are not.
* Files outside the declared output paths, and files under the distribution staging directory or host cache, are rejected.
* The same file produced with identical content by several partitions is written once. Different content, or names that
differ only in letter case, is a conflict: the build fails and nothing is written.
* Before writing, every destination is checked (no symbolic links or junctions, no directory in the way). Replaced files
are backed up and their permissions kept; if any step fails, all changes are rolled back. Commits to the same module are
serialized within the JVM and across JVMs using the staging directory’s `commit.lock`.
* A partition that crashed or did not complete fails the build, even when it reported no test results.

Staging uses `.citrus-dist-outputs/tx-*` and is removed afterwards. Downloaded blobs are kept in
`.citrus-dist/cache` under the Maven build directory (configurable with `citrus.test.distribution.cacheDir`; a relative value is resolved below
the module’s build directory) and are not evicted automatically. `citrus.test.distribution.cacheDir` only applies to the
caches of the build host and the coordinator. Workers keep their own local file cache, by default in
`${user.home}/.citrus-test-distribution-agent/file-cache` (see `citrus.test.distribution.worker.cacheDir` below).

The worker cache settings are also available as command line options (see <<tools-test-distribution-workers>>).
Command line options take precedence over system properties, which take precedence over the `CITRUS_DIST_WORKER_*`
environment variables and then their `TEST_DISTRIBUTION_AGENT_*` aliases. Blank values count as unset; invalid values
stop the worker with an error.

A worker runs one partition at a time; run several worker daemons per machine for more parallelism (tests that bind
fixed ports can then still collide across daemons on the same machine; use capabilities or separate hosts for them).
Each daemon needs its own `--cache-dir`: a worker locks its local file cache directory, so a second daemon using the same
(default) directory refuses to start (see <<tools-test-distribution-workers>>). Cancelling a
partition (lease expiry, lost connection, worker shutdown) kills the forked JVM and every process it started; nothing is
uploaded from a cancelled or crashed run. The forked JVM's `java.io.tmpdir` is a short `/tmp/cdtmp-*` directory on POSIX
systems so Unix domain socket paths stay within platform limits.
When a worker starts with the same cache directory and temporary directory settings, it also tries to remove the
private partition workspaces left by a worker JVM that was forcibly killed or called `Runtime.halt()`.
Recovery checks a matching ownership record and the identities of the worker and partition JVMs on the same host.
Workspaces are left in place if either JVM is still alive, a fork launch could not be confirmed, or ownership cannot be
verified. On Linux, recovery also requires the same boot and process namespace.

On Linux and macOS, the worker checks both directories for current filesystem references before removing a partition
workspace. An open file or working directory can keep both directories in place even after the worker and partition JVMs
exit. Linux uses `/proc` to check visible processes running under the worker's user identity and macOS uses the
system `lsof` command. On a clean forked workspace close, macOS checks surviving processes started at or after the
partition launch with targeted `lsof -p` calls and skips the full-host scan when none survive. This check excludes
processes that predate the launch. Use <<tools-test-distribution-workspace-lease,workspace leases>> for existing
long-lived helpers that use a workspace. Startup recovery, leased workspaces, in-process runs, and inconclusive targeted
checks still use full `lsof +D` scans. Cleanup is deferred if the check cannot complete. On Linux, a process that denies inspection
defers cleanup unless comparable kernel start times show that it predates the worker that created the workspace.
Such older processes are outside the check when they deny inspection. Unix socket paths are retained when the worker
cannot establish whether a listener still owns them.
On other platforms, the worker defers startup recovery and uses the platform's filesystem behavior during normal cleanup.
A process that only retains a path for future use has no current filesystem reference for the worker to check.

[[tools-test-distribution-workspace-lease]]
=== Workspace leases for background helpers

Set the test JVM system property `citrus.dist.workspace.lease.enabled=true` to let same-host Java helpers hold a
partition workspace after the partition ends. The enabled worker publishes an opaque local ticket as
`citrus.dist.workspace.lease.ticket` in the forked or isolated partition. Send the helper only this ticket, and wait for
it to acknowledge acquisition before allowing the partition to finish or forwarding any workspace path. A helper that
receives the ticket after cleanup starts may fail to acquire it and should stop the operation.

Use `org.citrusframework:citrus-test-distribution-protocol` on the helper's classpath. With the ticket as its first
argument, the helper can acquire the lease and get the workspace path as follows.

[source,java]
----
import java.nio.file.Path;
import org.citrusframework.distribution.workspace.WorkspaceLease;

try (WorkspaceLease lease = WorkspaceLease.acquire(Path.of(args[0]))) {
    Path workspace = lease.workspace();
    // Keep the lease open through every idle period and every use of the path.
}
----

Each helper acquires its own lease. The ticket and lease are local to the worker host and must be used by cooperating
processes under the worker's account on a filesystem with atomic file moves and cross-process file locking. Keep the
ticket private and close the lease when finished. The lease extends the lifetime of the workspace and its fork temp
directory. A helper that needs to survive a forked partition must run independently of its process tree. The worker
can terminate fork descendants on successful completion or cancellation.

If a helper exits abruptly, the operating system releases its lock. Cleanup closes admission to new leases. On Linux
and macOS, a later worker startup can reclaim deferred workspaces once the leases and filesystem references have
cleared. Startup recovery on other platforms retains orphaned workspaces.

[[tools-test-distribution-external-resources-compat]]
=== Requirements and caveats

* Partitions with inputs, outputs or `fork=true`, and partitions whose forwarded system properties contain the module
path, are only assigned to workers of this version (capability `citrus.workspace.v1`). With only older workers they wait
until the session times out.
* For host-specific Surefire JVM options and environment variables, configure the worker through
`forkJvmArgs` or system properties.
* A working directory under the configured Maven build directory retains its location in the worker workspace.
  Other working directories outside the module map to the workspace root.
* Without the Maven extension, invalid `fork` or `partitionPolicy` values are reported when the module runs distributed
rather than at build start.
* The forked JVM uses the worker's copy of the distribution protocol classes; keep hosts and workers on the same Citrus
version.
* Tests of a partition that crashed are missing from the Surefire reports; the build fails with the crash diagnostic.
* A test class the worker cannot find in the partition's classpath fails the partition (`Test class not found`) after
the partition's other tests have run.
* TestNG data-provider and invocation-count methods run on workers with either fork mode. With `AUTO`, the
  partition loads TestNG and its engine together from the module’s test classpath.
* In the shared worker JVM (`forkMode=AUTO`) the JUnit Platform, SLF4J and the Log4j API come from the worker; the tests
see no other worker classes except those of the worker's own `-javaagent` jars (for example a JaCoCo runtime).
* Worker cache eviction is exact least-recently-used ordering while a worker runs. After a restart, files last used
within the same file system timestamp interval are evicted in a fixed (deterministic) order, so the order across
restarts is only approximately least recently used.

[[tools-test-distribution-external-resources-limits]]
=== Limits

* The same limits apply to classpath directories such as `target/test-classes` (packaged for every distributed module):
no symbolic links or special files, valid names, at most 50,000 entries.
* Each blob (a file, or a directory packaged as ZIP) is at most 256 MiB compressed; an archive holds at most 50,000
entries, 256 MiB per entry and 2 GiB uncompressed in total.
* Symbolic links and Windows junctions in inputs or outputs are rejected, as are absolute paths, `..`, `:` and Windows
reserved names such as `CON` or `aux.json` (on every operating system, so workspaces stay portable).
* Forked partitions require JUnit Platform 6 on the module's test classpath. Because workers fork every partition by
default, modules on an older JUnit Platform need workers started with `forkMode=AUTO`.

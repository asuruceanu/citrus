3Now in scope: client & bidirectional streaming

The module previously stopped at unary and server-streaming calls (spec D3, "follow-up"). On this branch the client side was brought in scope; the two extra RPCs are now expressed with the same DSL vocabulary as the receive side.

The new DSL — sending and completing a client-streaming call

when(grpc().client(petStore).send()
        .call("grpc2grpc.PetStoreService/StoreUsers")
        .message().body(user(1, "ada")));          // opens the call, no half-close

when(grpc().client(petStore).send()
        .streamMessage().message().body(user(2, "bob")));

when(grpc().client(petStore).send().streamCompleted());  // completes the request side

then(grpc().client(petStore).receive()
        .response().message().validate(jsonPath().expression("$.msg", "@notEmpty()@")));

What was added

  • DSL: send().streamMessage() sends another message on the open call, send().streamCompleted() half-closes it; the first send() on a client-streaming or bidirectional method opens the call without half-closing.
  • Client endpoint: the call registry keeps the live ClientCall (queue, method, cancellation) so further messages can be sent on it and the request side completed; receives keep flowing through the same per-call queue.
  • Method types: CLIENT_STREAMING and BIDI_STREAMING are mapped end to end and appear as citrus_grpc_method_type on received messages.
  • Tests: three offline unit tests drive both kinds through the DSL against a real grpc-java server (client-streaming, bidirectional, and the "unknown call" failure); the live suite above covers them against Beeceptor.

Remaining for full alignment with the official branch

  • Simulator side — serving client-streaming/bidirectional calls (collect several request messages for one call, stream replies) is the larger half and is not part of this PoC.
  • Declarative DSLs — XML and YAML models do not expose the two new send actions yet.
  • Spec — lift D3 and add requirements for open calls, sending on an open call and completing it; the PoC stays on its own branch until that is agreed.

5Small change made for the PoC

Public endpoints are signed by well-known CAs, but the client could only trust a configured certificate file. On this branch only, GrpcTlsSupport.clientCredentials() gained a JVM-default-trust-store fallback:

// tls(true) without a trustCertificate now uses the JVM trust store
public static ChannelCredentials clientCredentials() {
    return TlsChannelCredentials.create();
}

6What this proves

  • Real-world protocol stack — TLS + HTTP/2 (ALPN h2), a public certificate, and a remote service, not an in-process stub.
  • Requirement coverage against a live peer — descriptor loading from .proto (GRPC-001), JSON request bodies (GRPC-002), unary calls (GRPC-006), server-streaming messages (GRPC-008), client cancel (GRPC-011) and TLS (GRPC-020).
  • Framework fit — the standard test action support (`@CitrusTest`, `@BindToRegistry`, Gherkin DSL, JSONPath matchers) works unchanged against an external gRPC service.
  • Interop — a vanilla gRPC server (Beeceptor's implementation) accepts Citrus's dynamic messages byte-for-byte: no reflection, no stubs, plain descriptors.

7Limitations & notes

  • Mock responses are randomized; the tests assert structure, not exact values.
  • The stream length from ListUsers is not predictable, so that scenario receives one message and cancels. When the length is known, streamCompleted() would assert the end of stream as well.
  • Beeceptor's BulkUsers mock echoes one message per received message when the client reads between sends; the live test follows that behavior. Server reflection is still out of scope for the module.
  • The endpoint is a shared, public Beeceptor instance. During the PoC an earlier endpoint hit Beeceptor's free-tier quota under heavy probing: calls then answer RESOURCE_EXHAUSTED ("Rate limit exceeded") and unary receives arrive with an empty payload. The suite was re-pointed at a fresh endpoint; a production setup would use a claimed/dedicated endpoint or mock service.
  • This report and the live tests live only on the disposable branch poc/686-grpc-live-beeceptor; the official feature/686-grpc-endpoint branch is untouched.

What was tested

GraphQLZero is a free, public GraphQL API serving the JSONPlaceholder data set from an Apollo Server. It has six related resources (users, posts, comments, todos, albums and photos) and exposes 12 queries and 18 mutations: for each resource a single-item query, a paginated list query, and create, update and delete mutations. The data is fixed and mutations are not persisted, so every response is deterministic. Created posts always come back with id 101, a deleted post always returns true.

That makes it a good opponent for a test framework. It is a third-party server the module was never built against, it follows the Apollo flavour of GraphQL over HTTP, and its answers can be asserted exactly.

How the tests were built

The schema was taken from the live API by running a full introspection query and converting the result to SDL with graphql-java. That file (graphqlzero.graphqls, 299 lines) is configured on every client, so each document is validated against the real schema before it is sent.

To make sure the three DSLs test exactly the same thing, the 30 operations were described once, in a table of document, variables and expected values, and the Java, XML and YAML tests were generated from it. Every expected value was first observed against the live API with plain HTTP calls.

Each operation is a send followed by a receive. The receive checks the HTTP status and several values in data. Any GraphQL error in the response fails the test automatically, since the module treats unexpected errors as failures even when the status is 200. The edge cases are hand-written Java tests.

GET with Apollo's CSRF preflight header

GraphQlZeroEdgeCasesIT.java
public void queryOverGetWithPreflightHeader() {
    var request = graphql().client(graphqlZero)
            .send()
            .get()
            .query("query GetPost($id: ID!) { post(id: $id) { id title } }")
            .variable("id", "1");
    request.message().header("apollo-require-preflight", "true");
    $(request);

    $(graphql().client(graphqlZero)
            .receive()
            .data("$.post.title", "sunt aut facere repellat provident occaecati excepturi optio reprehenderit")
            .message()
            .status(200));
}

Schema validation stops a bad query before it is sent

GraphQlZeroEdgeCasesIT.java
public void schemaRejectsUnknownFieldBeforeSending() {
    $(assertException()
            .exception(ValidationException.class)
            .message("@contains('isbn')@")
            .when(graphql().client(graphqlZero)
                    .send()
                    .query("{ post(id: 1) { isbn } }")));
}

Chaining a value from one response into the next request

GraphQlZeroEdgeCasesIT.java
public void chainValuesBetweenRequests() {
    $(graphql().client(graphqlZero)
            .send()
            .query("query GetPost($id: ID!) { post(id: $id) { user { id } } }")
            .variable("id", "11"));

    $(graphql().client(graphqlZero)
            .receive()
            .message()
            .extract(fromBody().expression("$.data.post.user.id", "authorId")));

    $(graphql().client(graphqlZero)
            .send()
            .query("query GetUser($id: ID!) { user(id: $id) { id username } }")
            .variable("id", "${authorId}"));

    $(graphql().client(graphqlZero)
            .receive()
            .data("$.user.id", "${authorId}")
            .data("$.user.username", "Antonette"));
}

Proof the tests can fail

A suite that passes on its first run proves little unless its assertions actually bite. So one expected value was changed on purpose in each DSL (user 1's username, from Bret to NotBret) and the operation tests were run again. Exactly the three affected tests failed, each naming the path, the expected value and the received value:

✗ GraphQlZeroJavaIT.users ✗ GraphQlZeroUsersXmlIT ✗ GraphQlZeroUsersYamlIT

Values not equal for element '$.data.user.username', expected 'NotBret' but was 'Bret'

The change was reverted afterwards and the full suite passed again.

What the real server taught us

Apollo · CSRF prevention

GET needs a preflight header

Apollo rejects GET requests that could be cross-site requests with 400 and code BAD_REQUEST. Adding apollo-require-preflight: true through the regular .message().header(...) was enough. No module change was needed.

GraphQL over HTTP

400 even for legacy JSON

For an invalid document Apollo answers 400 with both application/graphql-response+json and legacy application/json. The spec allows 200 for the legacy type, and Spring GraphQL does that. The module does not care: it checks errors whatever the status.

Data model

Unknown ids are not errors

post(id: 9999) returns an object whose fields are all null, with no errors. A whole-object data(...) comparison expresses that precisely.

Schema

The introspected schema loads as is

The 299-line SDL from introspection, with enums, input types and nested paginated types, loaded without any change, and caught the invalid isbn field before any network call. That check took 3 ms.

Limits of this PoC

  • The tests depend on a public service and the internet, so they belong on a PoC branch, not in the regular build.
  • Expected values come from GraphQLZero's fixed data set. A change to that data would break the tests, not the module.
  • Subscriptions are out of scope for the module and were not tested.
